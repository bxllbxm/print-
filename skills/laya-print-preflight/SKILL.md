# LAYA 인쇄 파일 점검

제작 전 기준을 잡고, 원본과 최종 납품 파일을 점검한다. [길벗의 8가지 기준](references/print-rules.md)을 먼저 읽는다. 자동 검사의 근거와 원본·시각·인쇄소 확인을 합쳐 판정하며, 확인되지 않은 항목을 통과로 처리하지 않는다.

## 입력과 제작 기준

- 대상 파일, 제작 앱, 최종 납품 형식(PDF/원본), 완성 재단 크기, 인쇄소의 도련·색상 프로파일·별색 요구를 기존 대화와 제공 자료에서 찾는다. 없는 정보만 필요한 시점에 묻고, 독립적으로 가능한 파일 검사는 계속한다.
- 제작 요청이면 작업 시작 전에 인쇄소 기준을 적용하고, 내보낸 최종 파일까지 검사한다. 검사 요청이면 원본을 읽기만 한다. 수정 요청을 받았을 때만 사본을 수정하고 다시 검사한다.
- 인쇄소가 명시한 해당 작업의 사양을 우선한다. 글의 기준과 달라지는 항목은 적용 기준·근거·차이를 기록한다. 미제공 사양을 임의로 확정하지 않는다.
- 제작 앱에서 중요한 글자·로고에 3–5mm 안전 영역을 확보한다. 인쇄소 요구가 없을 때 작업 목표로 5mm를 선택할 수 있으나, 이를 원문의 단일 필수값으로 설명하지 않는다. 도련 폭, ‘작은 글자’의 pt 경계, 리치블랙 배합은 원문에 없다.

## LAYA와 원본 앱

LAYA가 파일 분석기나 Adobe 편집기를 제공한다고 가정하지 않는다. 사용자가 LAYA를 통한 제작을 요청했을 때만 실제 설치된 기능을 확인한다. 앱 실행에는 사용 가능한 `laya-mac-control`/`laya-terminal` 스킬의 미리보기와 확인 절차를 따른다. `laya --help`에 없는 인쇄·내보내기 명령을 만들지 않는다.

Adobe 앱 이름이 자연어 별칭에 없으면 `laya-mac-control`의 앱 실행 도우미에 `--app`으로 실제 설치된 앱 이름 또는 경로를 지정하고 `--dry-run --json`으로 확인한다. 별칭 실패를 전체 LAYA의 부재로 해석하지 않는다.

현재 LAYA가 앱 실행만 지원하면 앱 실행은 LAYA로, 문서 조작은 제공된 앱 도구로, PDF 증거 수집은 아래 도구로 수행했다고 구분한다. 앱 조작 도구가 없으면 확인할 수 있는 PDF 항목부터 검사하고 원본 확인 항목을 남긴다. PDF 검사에는 LAYA 서버가 필요하지 않다.

InDesign 원본에서는 Preflight와 Links를 사용해 누락·변경 링크, 누락 폰트, 넘친 텍스트, 배치 이미지의 유효 해상도를 확인한다. 기본 프로파일의 녹색 표시만으로 모든 항목을 통과시키지 않는다. Illustrator 원본에서는 실제 문서 색상 모드, 링크, 스와치의 별색 여부, 작은 글자의 잉크 구성을 확인한다. 원본 앱·메뉴는 현재 화면에서 확인하고 조작한다.

최종 PDF 내보내기에서는 인쇄소의 페이지/스프레드, 도련, 출력 프로파일, 별색, 폰트 및 PDF/X 요구를 따른다. 프리셋 이름이나 확장자만으로 적합성을 확정하지 않는다. 편집 가능한 원본을 보존한다.

## PDF 증거 수집

`scripts/pdf_probe.py`는 **읽기 전용 부분 검사**이며 PDF/X 인증 도구가 아니다. 실행 가능한 Python 3와 `pypdf`를 사용한다. Codex에서는 `load_workspace_dependencies`가 반환한 Python을 우선 확인한다. 의존성이 없으면 사용할 환경에 설치하거나, 자동 검사를 못 했다고 기록하고 이용 가능한 앱 점검을 계속한다.

스킬 폴더 기준 예시 (`python3`는 확인한 실행환경의 실제 경로로 바꾼다):

```bash
python3 scripts/pdf_probe.py '/absolute/path/final-print.pdf' --json '/absolute/path/preflight-evidence.json'
```

인쇄소/사용자가 확인한 값이 있을 때만 `--trim-mm WIDTH HEIGHT`, `--bleed-mm MM`을 추가한다. `--min-ppi` 기본값은 글의 이미지 기준인 300이다. 다른 기준을 적용하면 출처를 기록한다. 출력 경로는 원본과 다르게 지정한다.

보고서의 파일 해시, 페이지, 박스의 명시 여부, 폰트, 발견된 색상·별색, 각 이미지 배치의 해상도와 `findings`/`manual_checks`를 읽는다. 종료 코드 1은 부분 검사 결과에 추가 확인이 필요하다는 뜻이며, 2는 입력·실행 오류다. `complete: false`는 전체 인쇄 적합성을 인증하지 않았다는 뜻이다. 종료 코드만 읽고 결론을 내리지 않는다.

- 명시된 TrimBox가 없으면 MediaBox/CropBox를 재단선으로 확정하지 않는다. `--trim-mm`은 크기 비교만 수행하며 재단 위치를 만들어 주지 않는다.
- BleedBox가 있어도 배경이 도련 끝까지 채워졌다는 증거가 아니다.
- 이미지 자원 해상도와 실제 배치 해상도는 다르다. 반복 배치, Form 변환, UserUnit을 포함한 결과를 읽는다. 지원되지 않는 변환·마스크·패턴 등은 추가 확인한다.
- 색 공간 자원이나 색 설정 연산자의 발견은 후보 증거다. 미사용 자원도 포함될 수 있으며, RGB 후보가 없다고 전체 CMYK로 판정하지 않는다. 작은 글자의 K 단색·리치블랙 여부는 원본 잉크값 또는 Acrobat 분판으로 확인한다.
- 기준 8의 문서 색상 점검에는 글자·벡터·그라데이션도 포함한다. 이미지가 없거나 별색이 없다는 이유만으로 RGB 문서를 CMYK 기준에 적합하다고 판정하지 않는다.
- 폰트 미포함은 주의 사항이다. 폰트 자원이 없다고 글자가 모두 아웃라인 처리됐다고 판정하지 않는다. PDF에는 포함된 폰트가 적절할 수 있다.

## 시각·원본 검토

가능한 PDF 렌더러로 최종 파일을 표시하고 페이지별로 재단·작업 영역을 구분해 살핀다. 전체 페이지와 문제가 의심되는 부분의 확대 화면을 확인한다. 일부 페이지만 검토했으면 검토 범위를 명시한다. 렌더링 실패나 원본 접근 불가를 확인됨으로 바꾸지 않는다.

8가지 기준의 위치·근거를 남긴다. 중요한 글자·로고에는 아웃라인 글자와 이미지 안의 글자도 포함한다. 단순 텍스트 추출만으로 안전 여백을 통과시키지 않는다. 테두리 검사는 재단 주변 프레임에만 적용하며 장식선·표 구분선에 일괄 3mm를 요구하지 않는다. RGB로 표시된 미리보기 색으로 C/M/Y/K 구성값을 판정하지 않는다. 별색 변환 뒤에는 시각 비교를 수행한다.

리치블랙의 건조·뒷묻음·페이지별 색 차이는 파일만으로 확정할 수 없다. 해당되는 경우 용지·인쇄 방식에 맞는 인쇄소 기준 또는 교정쇄 확인을 요청한다. 파일이나 원본을 변환·아웃라인 처리할 때는 사본에서 수행하고 다시 내보내 검증한다.

## 결과

한국어로 요점을 먼저 전달하고 **8개 항목을 빠짐없이** 표에 기록한다.

| 항목 | 판정 | 근거·페이지/대상 | 필요한 조치 |
| --- | --- | --- | --- |
| 기준 1–8을 각각 기재 | 확인됨 / 주의 / 확인 필요 / 해당 없음 | 실제 값, 사용한 기준, 검사 경로 | 구체적 수정·추가 확인 |

`확인됨`은 해당 범위를 실제 증거로 확인한 경우, `주의`는 기준 위반이나 후보가 발견된 경우, `확인 필요`는 자료·도구·인쇄소 사양이 부족한 경우다. `해당 없음`도 이유를 적는다. PDF에서 PDF 외 낱장 원본의 아웃라인 권고가 적용되지 않는다고 해도, PDF 폰트 포함 상태는 별도 근거로 남긴다.

예를 들어 글자와 페이지 가장자리 사이에 16mm가 있어도 재단선이 확정되지 않았으면 기준 1은 `확인 필요`다. 페이지 가장자리와의 거리는 참고 근거로만 기재한다.

결론에는 대상 최종 파일과 검사 범위, 우선 해결할 문제, 남은 확인을 쓴다. 모든 적용 항목의 근거가 모이기 전에는 ‘문제 없음/인쇄 가능’을 선언하지 않는다. 파일을 수정한 경우 최종 해시를 다시 기록하고 이전 버전의 결과를 재사용하지 않는다. 인쇄 실행·주문·전송은 점검 요청에 포함되지 않는다.

요청 예: `$laya-print-preflight 이 PDF를 길벗의 8가지 유의사항으로 검사해 줘. 완성 크기는 148×210mm, 인쇄소 도련은 사방 3mm야.`
